Sky365 Agent Platform Foundation

A consolidated decision document for Sim, Suna, Grok Build, the semantic-layer gap, deterministic business execution, and the next adoption step.

Date: 2026-08-01 Status: Draft for review Primary candidate: Sim Behavior reference: Suna Coding reference: Grok Build
Current Direction

One platform path, not three competing projects

Sim is the current code-foundation candidate. Suna is the digital-workforce behavior reference. Grok Build is a coding-agent reference and optional future worker. The semantic, ERP, security, approval, audit, and deterministic business layers remain Sky365-native.

Preliminary Match
7.8/10

Sim currently passes the 75% threshold, pending a full local repository audit.

Preferred Execution Pattern

Semantic first, deterministic by default

Semantic Understanding→ Deterministic Plan→ Bounded Agentic Work→ Validation→ Approval

Why Sim

  • Visual Agent Studio and workflow canvas
  • DAG-based workflow executor
  • Parallel execution queue
  • Pause, resume, snapshots, cancellation
  • Human-in-the-loop patterns
  • MCP and tool catalog integration points
  • Scheduling, logs, run metadata, background execution
  • TypeScript codebase with strong integration potential

What Sim does not solve

  • Sky365 business semantics
  • ERP metadata and controller awareness
  • Authoritative metrics and joins
  • Tenant and permission enforcement
  • Named business queries
  • Approval and audit contracts
  • Deterministic business routing

Suna's role

Suna is not the primary code foundation. It is the strongest reference for how a digital workforce should behave.

  • Supervisor and specialist agents
  • Task decomposition
  • Shared company context
  • Long-running work
  • Deliverable generation
  • Worker progress and status presentation

Grok Build's role

Grok Build is a coding-agent harness, not a business-agent platform.

  • Do not rewrite it in C#
  • Do not make it the Sky365 core
  • Study its agent loop, context, tools, ACP, MCP, plugins, and subagents
  • Potentially expose it later as one external coding worker

Critical Semantic-Layer Correction

The current agentic flow can perform worse than deterministic execution when the model is allowed to guess business meaning. Authoritative concepts must come from governed metadata, not prompt interpretation alone.

Must be resolved by Sky365LLM's proper role
Entity, metric, relationship, date grainPropose or interpret candidate meaning
Tenant, permission, business policyExplain the result
Named query, workflow, allowed actionPlan within approved boundaries
Draft, approval, or execution statusGenerate narrative, options, and clarification

First Benchmark

Create a ledger voucher draft from natural language:

  • Resolve both accounts
  • Capture amount, currency, dimensions, narration
  • Detect missing data
  • Validate balancing and policy
  • Save a draft
  • Request approval
  • Execute only after approval
  • Record the complete trace

Immediate Plan

  1. Clone Sim and Suna with GitHub CLI.
  2. Run a code-level architecture comparison.
  3. Confirm or reject Sim's 7.5/10 threshold.
  4. Document semantic and integration gaps.
  5. Select one adoption mode.
  6. Fork only after the decision.

Final Session Direction

Build Sky365 Agent around a reusable open-source visual workflow foundation only if it survives code-level assessment. Keep business semantics, metadata, policies, execution, permissions, approvals, and audit native to Sky365.

The next action is the local GitHub CLI assessment. It is not another broad search, not an immediate fork, and not immediate implementation.
